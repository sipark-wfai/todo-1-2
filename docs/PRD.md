## 1. 개요

### 1.1 배경
개인이 자신의 할 일을 한 곳에서 기록·분류·추적할 수 있는 웹 애플리케이션이 필요하다.
상용 TODO 앱은 기능이 과다해 학습·개인 사용 목적에는 오히려 진입장벽이 된다.

### 1.2 목적
**단일 사용자가 로컬 환경에서 실행하는, 할 일 관리에 필요한 최소한의 기능만 갖춘 웹 앱**을 만든다.
서버·클라우드 계정 없이 `npm run dev` 한 번으로 동작해야 한다.

### 1.3 제품 한 줄 정의
> 마감일·우선순위·태그로 할 일을 정리하고, 필터와 검색으로 지금 할 일만 골라볼 수 있는 개인용 TODO 웹 앱.

## 2. 범위 (Scope)

### 2.1 포함 (In Scope)
- 할 일 생성 / 조회 / 수정 / 삭제 / 완료 토글
- 마감일, 우선순위(3단계), 태그(다중) 부여
- 상태·태그·마감일 기준 필터, 제목·설명 텍스트 검색, 정렬 기준 선택
- 태그 생성 / 삭제
- SQLite 파일 기반 데이터 영속화 및 스키마 마이그레이션

### 2.2 제외 (Out of Scope)
| 제외 항목 | 사유 |
|---|---|
| 로그인 / 회원가입 / 다중 사용자 | 단일 사용자 전제 (§10 가정 A1) |
| 서브태스크 | 자기참조 계층 UI 비용이 MVP 가치 대비 큼 |
| 반복 일정 | 반복 규칙(RRULE) 모델링 난이도가 스코프를 크게 늘림 |
| 알림 / 리마인더 | 백그라운드 작업·푸시 인프라 필요 |
| 크로스 디바이스 동기화 | 로컬 SQLite 파일 전제와 충돌 |
| 드래그앤드롭 수동 정렬 | 정렬 기준 선택(FR-501)으로 대체. 순서 컬럼 도입 대비 이득 적음 |
| 파일 첨부, 코멘트, 공유 | 개인용 범위 초과 |

위 제외 항목은 §11 향후 범위에서 우선순위와 함께 다룬다.

## 4. 페르소나

### P-1. 지민 (주 사용자)
- **상황**: 업무와 개인 일이 섞여 있고, 마감이 있는 일과 없는 일이 뒤죽박죽이다.
- **행동**: 하루에 5~15개 할 일을 추가/완료한다. 대부분 한 줄 제목만 쓰고 넘어간다.
- **불만**: 상용 앱은 프로젝트·보드·워크스페이스 개념이 많아 시작 자체가 피곤하다.
- **성공 기준**: 앱을 열고 3초 안에 할 일 하나를 추가할 수 있다. "오늘 마감 + 높은 우선순위"를 한 번의 조작으로 볼 수 있다.

## 5. 에픽 · 피처 · 사용자 스토리

계층: **에픽(Epic) → 피처(Feature) → 사용자 스토리(User Story)**
사용자 스토리 형식: `As a [사용자], I want to [행동] so that [목적]`

### EP-01. 할 일 기본 관리
> 할 일을 기록하고 상태를 바꾸는, 앱의 존재 이유가 되는 기능군.

| 피처 ID  | 피처        | 설명                        |
| ------ | --------- | ------------------------- |
| FT-101 | 할 일 추가    | 제목만으로 즉시 추가, 상세 속성은 선택 입력 |
| FT-102 | 할 일 목록 조회 | 기본 목록 화면에서 전체 할 일 확인      |
| FT-103 | 할 일 수정    | 제목·설명·마감일·우선순위·태그 변경      |
| FT-104 | 완료 토글     | 완료 ↔ 미완료 전환               |
| FT-105 | 할 일 삭제    | 영구 삭제 (확인 후)              |

**사용자 스토리**

- **US-101** (FT-101) — 사용자로서, 제목만 입력하고 Enter를 눌러 할 일을 추가하고 싶다. 생각이 끊기지 않게 하기 위해.
  - 수용 기준
    1. 목록 화면 상단 입력창에 제목 입력 후 제출하면 할 일이 목록에 나타난다. 표시 위치는 현재 정렬 기준(FR-502)에 따르며, 마감일이 없는 새 할 일은 기본 정렬에서 뒤쪽에 놓인다.
    2. 제목이 공백만이면 저장되지 않고 입력창 아래에 오류 메시지가 표시된다.
    3. 제출 후 입력창이 비워지고 포커스가 유지된다.
    4. JavaScript가 비활성인 브라우저에서도 페이지 리로드 방식으로 추가된다.
- **US-102** (FT-102) — 사용자로서, 등록된 할 일 전체를 한 화면에서 보고 싶다. 무엇이 남았는지 파악하기 위해.
  - 수용 기준
    1. 각 항목에 제목, 완료 토글, 마감일, 우선순위, 태그가 표시된다.
    2. 할 일이 하나도 없으면 빈 상태 안내와 첫 할 일 추가 유도 문구가 표시된다.
    3. 마감일이 오늘보다 이전이고 미완료인 항목은 시각적으로 구분된다(색 + 텍스트 라벨 병기).
- **US-103** (FT-103) — 사용자로서, 등록한 할 일의 내용과 속성을 수정하고 싶다. 상황이 바뀌기 때문에.
  - 수용 기준
    1. 목록에서 항목을 선택하면 상세·수정 화면으로 이동한다.
    2. 제목·설명·마감일·우선순위·태그를 변경해 저장할 수 있다.
    3. 저장 시 `updated_at`이 갱신된다.
    4. 저장 실패 시 입력값이 유실되지 않고 화면에 유지된다.
- **US-104** (FT-104) — 사용자로서, 클릭 한 번으로 완료 처리하고 싶다. 완료가 가장 빈번한 동작이기 때문에.
  - 수용 기준
    1. 목록에서 완료 토글을 켜면 완료 시각이 기록되고 항목이 완료 스타일로 바뀐다.
    2. 다시 끄면 완료 시각이 제거되고 미완료로 돌아온다.
    3. 토글 후 현재 필터·검색·정렬 조건이 그대로 유지된다.
- **US-105** (FT-105) — 사용자로서, 필요 없어진 할 일을 삭제하고 싶다. 목록을 깨끗하게 유지하기 위해.
  - 수용 기준
    1. 삭제 실행 전 확인 단계를 거친다.
    2. 삭제된 할 일의 태그 연결도 함께 제거되고, 태그 자체는 남는다.
    3. 삭제는 복구되지 않는다는 점이 확인 문구에 명시된다.

### EP-02. 일정 관리
> 마감일을 부여하고 임박한 일을 드러낸다.

| 피처 ID | 피처 | 설명 |
|---|---|---|
| FT-201 | 마감일 설정/해제 | 날짜 단위 마감일 지정, 비울 수 있음 |
| FT-202 | 마감 임박·지남 강조 | 오늘 마감 / 지남 상태 시각화 |

**사용자 스토리**

- **US-201** (FT-201) — 사용자로서, 할 일에 마감일을 지정하고 싶다. 언제까지 해야 하는지 잊지 않기 위해.
  - 수용 기준
    1. 날짜 입력은 `<input type="date">`를 사용하고, 마감일 없음도 유효한 상태다.
    2. 과거 날짜도 입력 가능하다(이미 지난 일을 기록하는 경우가 있다).
- **US-202** (FT-202) — 사용자로서, 오늘 마감인 일과 마감이 지난 일을 목록에서 바로 구별하고 싶다. 급한 일을 놓치지 않기 위해.
  - 수용 기준
    1. 미완료 + 마감일 < 오늘 → "지남" 라벨 표시.
    2. 미완료 + 마감일 = 오늘 → "오늘" 라벨 표시.
    3. 구별은 색상만으로 하지 않고 텍스트 라벨을 병기한다 (NFR-401).

### EP-03. 우선순위 관리
> 같은 날 할 일 중 무엇을 먼저 할지 결정한다.

| 피처 ID | 피처 | 설명 |
|---|---|---|
| FT-301 | 우선순위 지정 | 높음 / 보통 / 낮음 3단계 |

**사용자 스토리**

- **US-301** (FT-301) — 사용자로서, 할 일에 높음/보통/낮음 우선순위를 주고 싶다. 무엇부터 할지 정하기 위해.
  - 수용 기준
    1. 새 할 일의 기본값은 "보통"이다.
    2. 목록에서 우선순위가 텍스트 또는 아이콘+텍스트로 표시된다.
    3. 우선순위 기준 정렬 시 높음 → 보통 → 낮음 순서다.

### EP-04. 태그 기반 분류
> 프로젝트·맥락 단위로 할 일을 묶는다.

| 피처 ID | 피처 | 설명 |
|---|---|---|
| FT-401 | 할 일에 태그 부여 | 하나의 할 일에 여러 태그 |
| FT-402 | 태그 생성 | 이름으로 태그 등록 (중복 불가) |
| FT-403 | 태그 삭제 | 태그 삭제 시 할 일은 유지 |

**사용자 스토리**

- **US-401** (FT-401) — 사용자로서, 할 일에 여러 태그를 붙이고 싶다. "업무"이면서 "긴급"인 일이 있기 때문에.
  - 수용 기준
    1. 상세·수정 화면에서 기존 태그 목록에서 다중 선택할 수 있다.
    2. 태그를 모두 해제한 상태도 유효하다.
- **US-402** (FT-402) — 사용자로서, 새 태그를 만들고 싶다. 내 분류 체계를 쓰기 위해.
  - 수용 기준
    1. 태그 이름은 공백 제거 후 1자 이상이어야 한다.
    2. 이미 존재하는 이름(대소문자 무시)은 거부되고 오류 메시지가 표시된다.
- **US-403** (FT-403) — 사용자로서, 쓰지 않는 태그를 삭제하고 싶다. 태그 목록이 늘어나면 선택이 어려워지기 때문에.
  - 수용 기준
    1. 삭제 시 해당 태그가 붙어 있던 할 일에서 연결만 제거되고 할 일은 삭제되지 않는다.
    2. 연결된 할 일 개수가 확인 단계에 표시된다.

### EP-05. 조회 · 탐색
> 전체 목록에서 "지금 볼 것"만 좁힌다.

| 피처 ID | 피처 | 설명 |
|---|---|---|
| FT-501 | 정렬 | 마감일 / 우선순위 / 생성일 기준 |
| FT-502 | 상태 필터 | 전체 / 미완료 / 완료 |
| FT-503 | 태그 필터 | 특정 태그가 붙은 할 일만 |
| FT-504 | 마감일 필터 | 오늘 / 이번 주 / 마감 지남 |
| FT-505 | 텍스트 검색 | 제목·설명 부분 일치 |

**사용자 스토리**

- **US-501** (FT-501) — 사용자로서, 정렬 기준을 바꾸고 싶다. 날짜순과 중요도순을 번갈아 보기 때문에.
  - 수용 기준
    1. 기본 정렬은 `마감일 오름차순, 마감일 없음은 뒤로, 동일 시 우선순위 내림차순`이다.
    2. 정렬 기준은 URL 쿼리 파라미터로 표현되어 북마크·새로고침 후에도 유지된다.
- **US-502** (FT-502~504) — 사용자로서, 상태·태그·마감일로 목록을 좁히고 싶다. 지금 할 일에만 집중하기 위해.
  - 수용 기준
    1. 필터는 조합 적용된다(AND).
    2. 현재 적용된 필터가 화면에 표시되고, 한 번에 초기화할 수 있다.
    3. 결과가 0건이면 "조건에 맞는 할 일이 없습니다" 안내와 필터 초기화 링크가 표시된다.
    4. 필터 상태는 URL 쿼리 파라미터로 표현되며, JavaScript 없이 GET 폼 제출로도 동작한다.
- **US-503** (FT-505) — 사용자로서, 키워드로 할 일을 찾고 싶다. 오래된 항목을 다시 찾기 위해.
  - 수용 기준
    1. 제목과 설명에서 대소문자 구분 없이 부분 일치 검색된다.
    2. 검색어는 다른 필터와 함께 적용된다.

### EP-06. 데이터 영속성 및 운영 *(기술 에픽)*
> 데이터가 유실되지 않고, 스키마 변경을 추적 가능하게 한다.

| 피처 ID | 피처 | 설명 |
|---|---|---|
| FT-601 | SQLite 영속화 | 로컬 파일 DB, 서버 프로세스 불필요 |
| FT-602 | 스키마 마이그레이션 | 버전 관리되는 마이그레이션 파일 |
| FT-603 | 백업 가이드 | DB 파일 복사 기반 백업 절차 문서화 |

**사용자 스토리**

- **US-601** (FT-601) — 사용자로서, 앱을 재시작해도 내 할 일이 남아 있기를 바란다. 데이터 유실은 앱을 못 쓰게 만들기 때문에.
  - 수용 기준
    1. 앱 프로세스를 종료·재시작한 뒤에도 모든 데이터가 조회된다.
    2. DB 파일 경로가 환경 변수로 설정된다.
- **US-602** (FT-602) — 개발자로서, 스키마 변경 이력을 파일로 남기고 싶다. 변경을 되짚고 재현하기 위해.
  - 수용 기준
    1. `db:generate`로 마이그레이션 SQL이 생성되고 저장소에 커밋된다.
    2. `db:migrate`로 빈 DB에서 최신 스키마까지 재현된다.
    3. `db:push`는 로컬 개발에서만 사용하며 운영 적용에 쓰지 않는다.

## 8. 기술 스택 및 설계 결정

| 영역 | 선택 | 근거 |
|---|---|---|
| 프레임워크 | SvelteKit 2 + Svelte 5 (runes) | 요구 스택. 서버 로드 + form actions로 점진적 향상이 기본 제공 |
| 어댑터 | `adapter-node` | `adapter-auto`는 서버리스로 붙어 로컬 SQLite 파일을 쓸 수 없음 |
| DB | SQLite (파일) | 요구 스택. 별도 서버 프로세스 불필요 |
| 드라이버 | `better-sqlite3` | 단일 사용자·로컬 전용이므로 동기 API가 코드를 가장 단순하게 유지. 원격 이전 계획이 없어 libsql의 이점(원격 Turso 동일 코드)이 불필요 |
| ORM | Drizzle ORM + drizzle-kit | 스키마에서 타입 파생(NFR-602), 마이그레이션 파일 생성(FR-603) |
| 스캐폴딩 | `sv add drizzle` (sqlite / better-sqlite3) | 서버 전용 배치와 `.env`를 공식 CLI가 처리 |
| 인증 | 없음 | 가정 A1 |
| 언어 | TypeScript strict | NFR-601 |

### 8.1 트레이드오프 기록

**better-sqlite3 vs libsql**
- 채택: `better-sqlite3`. 동기 API라 쿼리 함수에 `await`가 없고, 성능도 가장 좋다.
- 대가: 네이티브 모듈이므로 플랫폼별 리빌드가 필요하고, 나중에 원격 DB(Turso)로 옮기려면 쿼리 함수 전체가 비동기로 바뀐다.
- 전환 조건: 원격 DB 또는 다중 인스턴스 배포가 요구되는 시점. 그때 libsql로 교체.

**`push` vs `generate`+`migrate`**
- 로컬 스키마 탐색은 `db:push`로 빠르게, 확정된 변경은 `db:generate` → `db:migrate`로 파일에 남긴다.
- `db:push`는 마이그레이션 파일 없이 DB를 직접 변형하므로 운영 적용에 쓰지 않는다(FR-603, US-602).

| A1 | 사용자는 1명이며 인증이 필요 없다 | 인증 에픽 추가, ERD에 `users`·`sessions` 추가, 모든 쿼리에 소유자 조건 추가 → 대규모 변경 |

| A3 | 데이터 규모는 할 일 수천 건 수준이다 | 수십만 건 규모면 페이지네이션·FTS5 전문 검색 필요 |
| A4 | 마감일은 날짜 단위이며 시각·타임존을 다루지 않는다 | 시각 단위 마감·타임존 요구 시 저장 형식과 표시 로직 변경 |
| A5 | 브라우저는 최신 Chrome/Safari/Firefox다 | 구형 브라우저 지원 시 빌드 타깃 조정 |

### 10.2 리스크
| ID | 리스크 | 영향 | 완화 |
|---|---|---|---|
| R1 | SQLite 단일 writer로 쓰기 경합 발생 | 중 | WAL + `busy_timeout=5000` (NFR-201), 쓰기 트랜잭션 최소화 (NFR-105). 단일 사용자라 발생 확률은 낮음 |
| R2 | `better-sqlite3` 네이티브 모듈 빌드 실패 | 중 | Node 버전 고정, 실패 시 libsql 대체 경로 문서화 (§8.1) |
| R3 | DB 파일 손상 / 실수 삭제 | 높음 | 백업 절차 문서화 (FT-603, NFR-204) |
| R4 | 스코프 확장(반복 일정·알림 요구 유입) | 중 | §2.2 제외 목록과 §11 향후 범위를 승인 기준으로 사용 |
| R5 | 접근성 요구를 개발 종료 후에 검증 | 중 | 화면 단위 구현 시점마다 axe 검사 수행 |
